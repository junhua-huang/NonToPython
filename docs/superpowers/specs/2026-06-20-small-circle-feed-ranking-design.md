# 小圈子首页推荐流排序设计

## 背景

当前首页推荐流位于 `app/services/recommendation_service.py` 的 `get_personalized_feed()`。它已经做过分页、批量聚合加载和数据库索引优化，性能风险较前一版降低。但当前排序更偏“好友绝对优先 + 热度/兴趣辅助”，不适合活跃用户不多的小圈子。

产品定位已确认：探索页承担热门内容发现，首页推荐流应以新内容优先，保证小圈子里的新帖子更容易被看到。

## 目标

1. 首页以新内容为主，避免新帖被老热门或好友排序压住。
2. 好友/熟人内容只做加分，不做绝对置顶。
3. 热度只做轻量加分，避免首页变成热门榜。
4. 兴趣信号轻量扩展到用户发帖、点赞、评论过的帖子话题。
5. 限制同一作者刷屏，同时尽量保证每页返回满 `per_page`。
6. 保持现有接口返回结构兼容。

## 非目标

1. 不引入机器学习、embedding、复杂协同过滤。
2. 不新增曝光日志、seen-post 过滤或 feed session。
3. 不修改认证、前端路由或推荐接口路径。
4. 不改变探索页热门帖子定位。
5. 不完全排除用户自己的帖子，只通过作者多样性限制降低刷屏。

## 推荐策略

采用“新内容优先 + 轻推荐加分”的综合排序。

候选池仍然来自近期公开帖子：

- 新用户：最近 30 天。
- 老用户：最近 7 天。

排序不再使用好友作为第一排序层，而改为综合分：

```text
feed_score =
  freshness_score
+ friend_score
+ interacted_author_score
+ topic_score
+ engagement_score
```

权重方向：

- 新鲜度：最高权重。
- 好友/熟人：中低权重。
- 兴趣话题：低权重。
- 点赞/评论热度：低权重，并封顶。

## 数据来源

### 好友作者

继续使用 `friendships` 中 `accepted` 好友关系。

### 互动作者

基于当前用户点赞/评论过的帖子作者形成轻量作者偏好。为避免 join 膨胀，点赞和评论作者分数应分别聚合后再合并，或使用 `COUNT(DISTINCT ...)`。

### 兴趣话题

兴趣话题来自三类帖子：

1. 当前用户自己发过的帖子。
2. 当前用户点赞过的帖子。
3. 当前用户评论过的帖子。

这些帖子关联的 `post_topics.topic_id` 作为兴趣 topic 集合。

### 热度

热度使用当前候选帖子的点赞数和评论数：

```text
engagement = like_count + comment_count * 2
```

该分数只做轻量加分，并封顶，避免首页变成热门榜。

## 多样性

当前实现先取一页再过滤作者，过滤后可能不满一页。新设计改为：

1. 先取 `candidate_limit = per_page * 3 + 1` 条候选。
2. 对候选按同作者上限过滤。
3. 尽量补满 `per_page`。

同作者上限沿用轻量规则：

```text
max_posts_per_author = max(3, per_page // 5)
```

如果内容量不足或候选不足，可以返回少于 `per_page`。

## 返回兼容性

`/recommendations/feed` 返回结构保持兼容：

- `posts`
- `has_more`
- `current_page`
- `per_page`
- `algorithm`
- `is_new_user`
- `diversity_applied`

`algorithm` 可更新为 `small_circle_fresh_v1`，便于日志和调试区分。

## 测试策略

新增或调整后端源码/单元级测试，覆盖：

1. 首页推荐流算法标识更新为 `small_circle_fresh_v1`。
2. 好友不再作为第一层绝对排序，而是参与综合分。
3. 候选池多取 `per_page * 3 + 1` 后再做作者多样性过滤。
4. 兴趣话题来源包含发帖、点赞、评论。
5. 热度分数有封顶，避免压过新鲜度。

现有性能回归测试继续保留，确保批量加载和 `per_page` 限制不倒退。

## 风险和取舍

1. 仍然没有曝光去重，翻页排序在新帖/互动变化时可能抖动；本轮不解决。
2. 仍然是规则排序，不保证长期个性化最优；适合当前小圈子阶段。
3. 分数权重需要后续根据真实使用反馈微调。
4. 候选池多取会比当前单页多扫描一些行，但 `per_page` 已限制为 20，且相关索引已存在，风险可控。
